# ESP32 连接状态与断连恢复

ESP32 在 Codex 菜单的“连接”页显示设备到 PC 桥接、PC 桥接到 Codex 的连接状态。连接页同时提供网络、认证、状态光圈和任务提醒开关。

| 状态 | 设备显示 |
| --- | --- |
| WebSocket 断开 | PC 桥接已断开 · 正在重连 |
| WebSocket 刚连接，等待桥接状态 | PC 桥接已连接 · 正在同步 |
| 桥接正常停止服务 | PC 桥接正在停止 |
| 首包或心跳超过 8 秒未到 | PC 桥接无响应 · 等待恢复 |
| 桥接可用，Codex IPC 断开 | PC 桥接已连接 · Codex 已断开 |
| 两段连接正常 | PC 桥接 / Codex 已连接 |

桥接每 2 秒发送一次应用心跳；设备每 1 秒检查超时。因此静默异常通常在最后一次心跳或连接建立后的 8–9 秒显示。心跳独立于任务消息与 WebSocket Ping，空闲任务不会被误判为断开。

```json
{"type":"bridge_status","version":1,"state":"ready","codexConnected":true}
```

`state` 为 `ready` 或 `stopping`。新设备连接、设备请求 `codex_sync`、Codex 连接变化时立即发送。正常关闭桥接时先发送 `stopping`，再结束连接。心跳不会写入桌面逐条消息日志。

失去可用连接时保留已显示的对话，清除任务控制状态、等待中的操作及录音状态，停止状态环和录音动画。连接仍可写入时发送取消听写，禁止自动提交。恢复后请求新快照，相同 revision 的恢复快照也可重新同步；迟到任务消息不能代替心跳恢复控制。

底层 WebSocket 配置为 5 秒 Ping、5 秒 Pong 等待、1.5 秒重连等待。正常关闭与网络异常均可自动重连当前地址。音频故障使用明确的 `Reconnect()` 重建连接；用户主动断开仍保留独立语义。PC 地址改变时，通过连接菜单重新搜索 PC。

Codex IPC 的实际 `close/error` 会立即使设备操作失效并取消听写。每次重连重新发现任务 owner，旧 socket 的事件、异步响应和缓存不能恢复在线状态，只有新快照可重新标记任务已同步。本次没有添加未经验证的 Codex 原生探测请求，因此管道仍打开但 Codex 进程完全卡住的情况尚无独立活性探测。
