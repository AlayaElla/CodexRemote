# 取消后再次按住说话的启动延迟

日期：2026-09-14。PC 版本：0.1.14。

## 问题

0.1.13 在普通取消时仍关闭音频 helper 和 WASAPI 通道，最多等下一次 2 秒维护检查才重新准备。每次按下还会新建 PowerShell 进程、加载原生类型、枚举应用及 UIA 元素。即使音频已准备好，窗口核验开销依然存在。

## 修改

- 普通取消使用新的 `discard` 操作：停止接收本次音频、清空 PCM、重置 Opus 解码器及会话计数，保留静音输出端点和进程。等待 350 毫秒让已进入系统输出管线的旧数据离开，再允许下一次使用。
- 准备阶段取消也复用通道。故障、配置切换和程序退出仍关闭通道；旧 helper 不支持 discard 或操作失败时清理并重新准备。
- PC 启动时预建只读窗口核验进程。每次检查重新获取 UIA 树和输入框身份，批量读取属性；只复用进程、程序集和安装位置。该驻留进程不接受发送按键或调用 UI 按钮的请求。
- 仍按任务 ID 导航，并保留导航后的 350 毫秒等待。输入目标检查未跳过。
- `Voice start timing (ms)` 日志记录连接、音频准备、任务核验和 HID 投递四段耗时。

## 本机测量

音频测量使用实际 VB-CABLE 输出端点，只输出静音，不采集麦克风，不触发 Codex 听写。

| 阶段 | 耗时 |
| --- | --- |
| 首次准备 | 2190.30 ms |
| 关闭 helper 后重新准备（模拟旧取消路径） | 1962.76 ms |
| 保留通道，取消后开始第 1 次 | 0.0149 ms |
| 保留通道，取消后开始第 2 次 | 0.0118 ms |
| 保留通道，取消后开始第 3 次 | 0.0150 ms |

三次循环保持相同 helper PID，开始时音频计数为零。丢弃阶段为 357–367 ms，发生在取消过程，包含系统音频输出保护等待。

驻留核验进程后台准备为 1445.7 ms；随后三次未知目标的只读拒绝检查为 170.7–198.5 ms。这是对窗口读取路径的测量，并非完整有效任务导航、HID 投递或 ESP32 端到端响应时间。

## 验证

原生 C# 自测验证连续三次 discard 清空缓冲、复位解码及计数、保持输出未关闭，并保留原有取消/排空/故障测试。Node 测试验证端点及进程复用、普通及准备阶段取消、恢复和退出、队列隔离；窗口 checker 测试覆盖常驻复用、只读消息边界、超时重启、迟到错误及退出清理。既有原生操作脚本仍通过 Windows PowerShell 完整解析及输入结构检查。

交付 `build/pc/CodexRemote-Portable-0.1.14.exe`。本次只修改 PC 端，继续使用上一版含上滑取消手势的 ESP32 固件。未自动替换用户运行中的 PC 进程或刷写设备，设备端实际等待需要更新 PC 后联调确认。
